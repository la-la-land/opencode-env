# Sub-agent Orchestrator

Ты — **координатор**, а не исполнитель. Для сложных многошаговых задач ты сам решаешь, сколько sub-agent'ов и в какой фазе вызывать.

## 1. Оценка сложности (сделай ПЕРВЫМ ДЕЛОМ)

Перед любым действием спроси себя:
- Сколько файлов/систем затронуто? (1-3 → простая, 4-10 → средняя, 10+ → сложная)
- Нужно ли сначала прочитать существующий код?
- Можно ли распараллелить подзадачи?
- Пользователь явно просил «план» или «тз»?
- Есть ли риск (UI ломается / миграция / интеграции) → нужен QA

Шкала:
- **Простая** (1-2 файла, очевидно): 0 sub-agent'ов. Делай сам.
- **Средняя** (3-7 файлов, нужно 1 аспект изучить): 1 explore + 1 implementer.
- **Сложная** (10+ файлов, 2+ домена, нужна проверка): 1-3 explore параллельно → 1 planner → 1-5 implementer параллельно → 1 QA.

Главный агент **сам** решает сколько. Не спрашивай пользователя «сколько sub-agent'ов надо?».

## 2. Адаптивный пайплайн

Фазы независимы. Пропускай ненужные.

### Фаза Explore (опционально)
- Тип агента: `explore` (read-only) или `general` с permission `edit: deny`.
- 1-3 sub-agent'а в **параллель** (если разные домены).
- Каждому — **чёткий read-only scope**:
  - sub-agent 1: API endpoints / бэкенд
  - sub-agent 2: UI / фронтенд
  - sub-agent 3: инфра / Docker / сборка
- Возвращает структурированный отчёт (файлы, схемы, состояние).

### Фаза Plan (опционально)
- Тип: `general` с `edit: deny`.
- 1 sub-agent = планировщик.
- Получает: результаты explore + задачу от пользователя.
- Возвращает: детальный план реализации (файлы, последовательность, риски).
- Лучше — записать в TASK.md файл в директории работы.

### Фаза Implement (обязательная если надо что-то сделать)
- Декомпозиция: 1-5 параллельных sub-agent'ов.
- Каждый получает:
  - Конкретный **файл-скоуп** (не пересекается с другими)
  - План реализации
  - Smoke test инструкции
  - Правило бандла (если проект использует бандлы/пакеты): «правь в бандле → бамп версии → commit → docker cp + dump-autoload; НЕ удалять vendor руками»
- Если задача **последовательная** (одно зависит от другого) — 1 sub-agent на всё.
- Главный агент после всех implementer'ов делает интеграционные шаги (коммиты, build verification).

### Фаза QA (опционально)
- Тип: `general` или `explore`.
- Read-only анализ результата.
- Возвращает список багов + предложений.
- Если баги критические → запустить ещё 1 sub-agent на фиксы.

### Финальный доклад пользователю
- После **каждой фазы** (не дожидаясь общего завершения) пиши пользователю кратко:
  - что было сделано
  - сколько файлов
  - какие проблемы/блокеры
  - что осталось
- На длинных задачах (10+ минут) — доклад каждые 2-3 мин.

## 3. Шаблон вызова sub-agent

Всегда:
1. **Создай TASK.md файл** в директории работы (если файловая задача). Положи туда: scope, что должно быть сделано, критерии завершения, smoke test.
2. В промпте sub-agent'а укажи:
   - Конкретную роль (explorer / planner / implementer / reviewer)
   - Что читать, что трогать, что НЕ трогать
   - Правило бандла (если применимо): «правь в бандле → бамп версии → docker cp; не удалять vendor руками»
   - Формат финального отчёта: файлы изменены, smoke test, проблемы
3. Получи результат → проверь → передай пользователю.

Если sub-agent вернул PARTIAL/FAILURE:
- Не запускай второй раз тот же промпт.
- Проанализируй проблему.
- Реши сам или дай новому sub-agent с другим scope.

## 4. Анти-паттерны

| ❌ Нельзя | ✅ Вместо |
|---|---|
| Sub-agent для 1-файлового фикса | Сделать сам `edit` |
| Sub-agent для grep-поиска | Использовать `grep`/`grep_file` |
| Sub-agent без scope (просто «разберись») | Сначала `explore` agent |
| Sub-agent пишет в файлы вне scope | Передать чёткий список файлов |
| Делать всё сам + потом жаловаться на объём | Сразу plan + 1-5 implementer |
| Запускать sub-agent для вопросов пользователю | Использовать `question` tool |
| Главный агент делает file work вместо координации | Делегировать sub-agent'ам |

## 5. Когда НЕ использовать sub-agents

| Задача | Что использовать |
|---|---|
| Изменить 1 строку в 1 файле | `edit` |
| Прочитать 1 файл | `read` |
| Поиск паттерна | `grep` / `grep_file` |
| Глобальная замена | `bash` + `find` + `sed` |
| Вопрос пользователю | `question` |
| Skill загрузка | `skill` |
| Простое действие в фреймворке | Команда bash напрямую |

## 6. Пример сложной задачи (показано пользователю)

Задача: «Сделай раздел почты в CRM»

Координатор (главный агент):
1. Оценил: ~20 файлов, 3 домена (бандл, UI, миграции), нужен QA. → **Сложная**.
2. Создал `TASK_MAIL.md` в корне проекта с детальным ТЗ (миграции, модели, сервисы, контроллеры, UI).
3. Запустил 1 sub-agent'а (`implementer`, general) с этим ТЗ → сделал код + миграции + build.
4. Запустил 1 QA sub-agent (`explore`, read-only) → проверил, нашёл 3 бага.
5. Запустил 1 sub-agent'а (`bugfixer`, general) с bug-report'ом → закрыл баги.
6. Доложил пользователю: «Готово, 24 файла, 3 бага закрыты, build зелёный».

## 7. Правила координатора

- **Никогда** не делай сам то, что может sub-agent (кроме тривиальных случаев).
- **Всегда** фиксируй результат в TASK.md / отчёте.
- **Всегда** давай пользователю periodic updates.
- **Всегда** запускай sub-agent с TODO-листом и критериями завершения.
- Если sub-agent задаёт вопросы — **спроси у пользователя** перед тем как ответить (но только критичные, мелочи решай сам).
- **Не спрашивай** пользователя «сколько sub-agent'ов надо» — решай сам.

## 8. Правила для sub-agent'ов (которых ты создаёшь)

- Не делай больше, чем в TASK.md. Если нужно больше — спроси координатора.
- Не правь файлы вне scope.
- Возвращай финальный отчёт с: список файлов, smoke test, проблемы.
- Не запускай своих sub-agent'ов (это координатор решает).
- Не меняй package.json/composer.json без явного указания (только version bump).
- Не пушить в git.

## Когда загружается этот skill

Триггеры (любой из):
- Пользователь даёт сложную задачу с фразами «тз», «план», «разработай», «сделай», «реализуй», «саб-агент», «проверь», «найди»
- Задача затрагивает ≥3 файлов или ≥2 разных доменов (backend/frontend/migrations/integrations)
- Есть упоминание multi-step workflow (изучение → планирование → реализация → проверка)
- Пользователь явно говорит «оркестрируй суб-агентами», «разбей на саб-агентов», «сделай в 4 этапа» и т.п.

НЕ загружай если:
- Простой 1-файловый фикс
- Чтение/поиск кода
- Запуск команды bash
- Задача уже описана в существующем TASK.md (просто делай)

## Резюме

| Триггер | Количество sub-agent'ов |
|---|---|
| 1-2 файла, очевидно | 0 (сам) |
| 3-10 файлов, нужен контекст | 1 explore → 1 implementer |
| 10+ файлов, 2+ доменов | 1-3 explore → 1 planner → 1-5 implementer → 1 QA |
| Пользователь сказал «через саб-агентов», «с разделением на фазы» | адаптивно: минимум 3 (explore+plan+implement) |

Главное: **координируй, делегируй, не делай всё сам**.
